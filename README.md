# se-vks-platform

Declarative record of the SE VKS environment on the **wld-sup** Supervisor
(`wkld01.vks.lab`): Supervisor services, the `se-namespace` vSphere Namespace,
the `se-cluster-01` cluster, its add-ons, and the applications running on it.

Plain manifests applied with `kubectl`, driven by a `Makefile`. No GitOps
controller.

## The one thing to understand first

**Two API endpoints are involved, and they are not interchangeable.**

```
Supervisor  (kubectl vsphere login --server=<wld-sup-vip>)
  ├── supervisor-services/                      SupervisorService, supervisor-wide
  └── namespaces/se-namespace/
      ├── 00-namespace.yaml                     the vSphere Namespace
      └── clusters/se-cluster-01/
          ├── 00-cluster.yaml                   the Cluster
          └── addons/                           AddonConfig + AddonInstall

Workload cluster  (same login + --tanzu-kubernetes-cluster-name=se-cluster-01)
  └── namespaces/se-namespace/clusters/se-cluster-01/
      └── workloads/                            your applications
```

`addons/` and `workloads/` sit side by side because both describe one cluster,
but they go to **different API servers**. Each carries a README saying which.

## Environment

| | |
|---|---|
| Supervisor context | `wld-sup` (`wkld01.vks.lab`) |
| vSphere Namespace | `se-namespace` |
| Cluster | `se-cluster-01` |
| ClusterClass | `builtin-generic-v3.7.0` (newest this Supervisor offers) |
| Kubernetes | `v1.35.6+vmware.2` |
| VM class | `best-effort-medium` |
| Storage policy | `vsan-default-storage-policy` |

ClusterClass and Kubernetes version are modelled on working clusters already on
this Supervisor. To re-check what is on offer:

```sh
kubectl --context=wld-sup -n vmware-system-vks-public get clusterclass
kubectl --context=wld-sup get cluster -A -o json \
  | jq -r '.items[] | "\(.metadata.name)  \(.spec.topology.classRef.name)  \(.spec.topology.version)"'
```

## Apply order

Each step depends on the one before it.

```sh
make services     # 0. Supervisor services       -> Supervisor
#    1. CREATE THE NAMESPACE IN VCENTER  <-- not a manifest, see below
#       Workload Management > Namespaces > Create Namespace
#       name se-namespace, add storage policy, add VM class, grant permissions
make preflight    # 1b. verify vCenter actually bound storage + VM class
make cluster      # 2. Cluster                   -> Supervisor
make addons       # 3. Add-ons                   -> Supervisor
make login-wl     # prints the workload-cluster login command
make workloads    # 4. Applications              -> workload cluster
make status       # where everything stands
```

`make preflight` exists because of the failure described below. Run it; it takes
a second and saves an hour.

## What cannot live in git

A vSphere Namespace is a vCenter construct. **On this Supervisor the namespace
itself cannot be created from a manifest at all** -- applying
`namespaces/se-namespace/00-namespace.yaml` is rejected:

```
admission webhook "default.validating.namespace.supervisor.vmware.com" denied
the request: User is not authorized to create selfservice namespaces
```

Manifest creation only works where Namespace Self-Service is enabled and granted.
It is not enabled here. Beware two misleading signals: `kubectl auth can-i create
namespaces` returns `yes`, and `kubectl apply --dry-run=server` reports success.
Neither reflects what a real apply does.

These likewise have **no manifest form** and are attached in vCenter:

- the namespace itself
- storage policy binding
- VM class binding
- namespace permissions / RBAC
- CPU and memory limits on the namespace resource pool

`00-cluster.yaml` references `vmClass: best-effort-medium` and
`storageClass: vsan-default-storage-policy` **by name**. If those are not bound
to `se-namespace` in vCenter, the Cluster will not provision and the failure is
not obvious. That is what `make preflight` checks.

Likewise, the labels and annotations on a live namespace (`vSphereClusterID`,
`nsx.vmware.com/vpc_network_config`, `aviinfrasetting.ako.vmware.com/name`) are
generated by vCenter. Never author them.

## Layout

```
se-vks-platform/
├── Makefile
├── supervisor-services/          -> Supervisor, install once
├── clusterclasses/               custom ClusterClasses (vmware-system-vks-public)
├── namespaces/
│   └── se-namespace/
│       ├── 00-namespace.yaml
│       ├── README.md             what is in git vs vCenter-only
│       └── clusters/
│           └── se-cluster-01/
│               ├── 00-cluster.yaml
│               ├── addons/       -> Supervisor
│               └── workloads/    -> workload cluster
└── _templates/                   copy to start another namespace or cluster
```

Numeric prefixes encode apply order: `kubectl apply -f <dir>` sorts
alphabetically, so `00-` before `10-` gives correct ordering for free.

## Adding another namespace or cluster

```sh
cp -r _templates/namespace namespaces/<new-ns>
grep -rn 'CHANGEME\|CLUSTER' namespaces/<new-ns>    # replace all of these
```

## Finding what is installable

```sh
# add-ons and their exact release names (needed for releaseFilter)
kubectl --context=wld-sup -n vmware-system-vks-public get addonreleases

# an add-on's configurable values
kubectl --context=wld-sup -n vmware-system-vks-public \
  get package <name> -o jsonpath='{.spec.valuesSchema.openAPIv3}' | jq .
```

## Secrets

Nothing here should contain a credential. Certificates and passwords are created
out of band:

```sh
kubectl -n <ns> create secret tls <name> --cert=<path> --key=<path>
```

`.gitignore` excludes key, certificate and kubeconfig files as a backstop, but
the rule is that secrets are never committed in the first place.
